## Context

Agent Server checkpoints are durable execution state, not cross-session memory. Private memory must use the supported Agent Server-injected `BaseStore` interface in application-owned namespaces. Documentation requires an independently authorized corpus boundary. Phase 5 supports one person per private installation and one separate database per installation; it defines no work members or shared/work memory.

## Goals / Non-Goals

**Goals:**

- Centralize server-side authorization for memory and documentation.
- Derive the opaque tenant, `local-installation-v1` trust domain, and `person` owner from trusted server configuration.
- Preserve bounded memory, immutable provenance, explicit creation, deterministic non-semantic memory retrieval, Store-native semantic documentation retrieval, and enforceable deletion.
- Preserve one canonical installation-wide, grounded documentation corpus and complete the deterministic authenticated-owner upload-to-OCR ingestion path, with canonical document-level tags and no per-session document-content copies.
- Restore a bounded set of stable linked document IDs with each authoritative thread and provide only the narrow Installation Library and Session Documents UI over server-authorized contracts.
- Keep application code away from Agent Server internal PostgreSQL tables and all persistence credentials away from agents.

**Non-Goals:**

- Shared/work memory, work-member policy, checkpoint migration, checkpoint-derived memory, direct specialist communication, MCP, UI work other than the narrowly specified Installation Library and Session Documents views, custom or unrelated vector infrastructure, semantic memory retrieval, ontology, reindexing workflows, and document/corpus deletion. The supplied Store's configured semantic index is in scope only for documentation fragments. Removing a session-document link is reference removal, not document deletion.

## Decisions

### 1. Separate memory and documentation authorities

Memory and documentation both use the supported Agent Server-injected `BaseStore`, in separate server-derived application namespace families. Documentation has exactly one server-derived canonical corpus per installation. Each document and its fragments are stored once in that corpus; sessions never copy document content. There are no direct PostgreSQL memory or corpus tables, and neither capability may select or write Agent Server internal tables or query the other. Production documentation starts empty.

### 2. Use the documented Agent Server database boundary

The trusted standalone Agent Server service receives the documented `DATABASE_URI` and owns its persistence and migration responsibilities. Browser, owner, Jasper, Coder, Librarian, and OCR identities are HTTP/auth-capability principals, not SQL roles, and receive no database URI. Phase 5 does not add PostgreSQL roles, ownership-transfer SQL, row-level security, direct SQL adapters, a custom Store/checkpointer, or a table allowlist.

The existing application-owned `session_catalog` connection is outside the Phase 5 memory/document persistence boundary. Its deployment hardening must not become a second Phase 5 authorization system. Database service-account hardening is an installation operation that must follow the selected Agent Server version and operator environment; LangGraph does not publish a stable internal-table privilege manifest for Phase 5 to reproduce.

Memory and documentation share one Agent Server Store service connection. The supported integration supplies namespaces, not a per-namespace SQL principal or connection selector. Their separation is therefore enforced by default-deny application capabilities and server-derived namespaces, not PostgreSQL row privileges. The underlying Store relation is an internal implementation detail rather than an application integration boundary.

### 3. Resolve one private installation scope server-side

Trusted configuration generates or loads one opaque tenant ID and owner ID, fixes owner type `person` and trust domain `local-installation-v1`, and supplies the only valid scope. Prompts, browser values, tools, and agent output cannot select scope. Missing, conflicting, shared, or work scope fails closed.

### 4. Enforce independent least-privilege operations

The owner may receive memory read, explicit write, exact delete, exact restore, permanent delete, owner-only audit access, documentation read/search, and current-thread document-link add/remove access. Jasper, Coder, and Librarian may receive bounded delegated memory operations; OCR cannot. Jasper, Coder, Librarian, and OCR may receive explicit documentation-read delegation. Jasper may add a document link only to the authoritative thread of its current run and only when it actually uses an authorized retrieval result. Corpus writes require a current supervisor-created ingestion delegation. Infrastructure operators have no default content access.

### 5. Use explicit namespace families

- Memory: `app / v1 / cross-session-memory / tenant:{id} / trust:{id} / owner:person:{id} / kind:{kind}`
- Documentation: `app / v1 / documentation-retrieval / tenant:{id} / trust:{id} / owner:person:{id} / corpus:{canonical-installation-corpus-id} / record:{type}`
- Sanitized audit: separately permissioned and never a content namespace.

Identifiers are normalized, opaque, bounded, and server-derived. Prefix enumeration is not agent-visible.

### 6. Store bounded memory envelopes with explicit creation

Each memory ID has exactly one current Store item in its server-derived kind namespace. An envelope includes schema version, immutable ID, kind, bounded content/metadata, server scope, provenance, timestamps, lifecycle state, a simple integer revision, deterministic operation ID, and request digest. There are no revision namespaces/items, materialized head copies, memory operation manifests, or capability tokens. Kinds are exactly `user preferences`, `user-provided facts`, `project decisions`, `task outcomes`, and `reusable instructions`. Per-kind and request limits are those in the capability spec. Limits never trigger automatic eviction.

Explicit create validates the complete request before writing. Its memory ID is derived from owner, kind, and operation ID; the one item carries the canonical request digest so a sequential identical retry returns that item and a conflicting reuse is rejected. No checkpoint, thread, message, tool result, report, or artifact becomes memory merely by existing. The design assumes neither compare-and-swap, multi-key transactions, conflicting-write safety, nor atomic checkpoint/Store writes. Revisions and stale-input checks are application validation only, not atomic CAS. Phase 5 does not add locks, read-back reconciliation, or a custom transaction protocol to simulate guarantees absent from the Store.

### 7. Make retrieval inspectable and use native semantic search for documents

Memory retains exact lookup, allowlisted metadata filters, and bounded application-level same-word lexical matching. Documentation supports stable-key exact lookup, allowlisted canonical document metadata filtering, and native semantic content retrieval. Exact document and fragment lookup uses `BaseStore.aget` with the full authorized namespace and stable exact Store key. Semantic retrieval calls `BaseStore.asearch` with the validated query against only the fully authorized fragment namespace and preserves the Store's returned order and score under existing candidate, result, query, and response bounds. Application code does not call the handcrafted `lexical_rank` function for documents and adds no reranking.

The documented `store.index` configuration uses the custom async function path `embed: ./src/phase5_embeddings.py:aembed_texts`, with `dims: 768` and `fields: [content]`. The adapter constructs LangChain's `OllamaEmbeddings` for `embeddinggemma`, resolves the trusted `OLLAMA_HOST` or `OLLAMA_BASE_URL` endpoint, and sets `keep_alive=0` so the model is unloaded after each embedding request. Compose points the endpoint to `http://host.docker.internal:11434` inside the user-approved `local-installation-v1` trust boundary. Container-to-host reachability and local model presence are verified before release. Canonical content-free document metadata is written with `index=False`; only content-bearing fragments are written with `index=['content']`. A document owns one canonical metadata envelope, including document-level tags. Tags remain returned and filterable through canonical metadata search and are not duplicated onto fragments. Documentation results include corpus, document, fragment/locator, title, canonical tags, approved URI or opaque locator, source revision, digest, source-time status, retrieval time, native score for semantic results, and truthful match mode. Unknown provenance stays `unknown`. Retrieved text is untrusted data and cannot affect authorization. Ontology expansion, custom vector stores, custom graph branches/routes, custom reranking, and reindexing workflows remain out of scope.

### 8. Enforce the approved memory lifecycle

Memory remains until owner deletion. Exact deletion overwrites the one current item as deleted, immediately excludes it from every normal read, and sets a per-item native Store TTL. The exact owner can restore through the inclusive logical cutoff at `deleted_at + 7 days`; restore rewrites active state and explicitly clears TTL. After that instant restore is denied even if asynchronous physical sweeping has not removed the item. Owner-authorized permanent delete physically deletes the exact item immediately.

The configured Store TTL policy disables refresh-on-read, defines no default TTL (so active memory and documentation do not expire), and runs only the native sweeper every 60 minutes. Deleted-memory and audit TTLs include one sweep interval of physical padding so the Store cannot normally remove an item before its inclusive logical boundary. Native TTL deletion is best-effort and asynchronous: an item may remain physically present after logical expiry until a later sweep, and a backend sweep or outage offers no exact physical-deletion-time guarantee. Logical read/restore rules therefore remain authoritative. There is no application memory or audit purge scheduler.

Content-free memory audit events are owner-only, carry a per-item native TTL, and have an exact logical expiry at 90 days enforced on read. They contain identifiers, operation, decision/reason class, correlation, time, and counts, never memory bodies, credentials, or internal reasoning.

### 9. Preserve approved documentation ingestion

The implemented production callers are intentionally limited to manual actions by the authenticated human owner in **Installation Library**. For a file, the owner explicitly selects one sidecar-supported document; the sidecar preserves its original bytes and returns an opaque `upload:` reference. For a public source, the browser submits only a bounded HTTPS URL, bounded title, and optional bounded tags to a second narrow custom route. Both routes verify auth-first `Request.user` exactly against installation identity and obtain the Agent Server-injected `BaseStore` through documented `langgraph.config.get_store()`. Tenant, corpus, requester, routing authority, document/fragment/operation IDs, source status, revision, digest, and locator are server-derived. Successful results return only document ID and fragment count and do not automatically link the document.

The public route's trusted backend downloader permits HTTPS on port 443 only, rejects userinfo/fragments/local names and non-global or mixed DNS answers, resolves before each fresh connection, connects to one validated IP while preserving TLS SNI/certificate hostname verification and the HTTP Host header, disables implicit redirects and revalidates at most five Location hops, ignores proxy environment configuration, and bounds timeout, headers, accepted PDF/HTML/plain-text media types, and body bytes to the existing 25 MiB ceiling. It derives a safe extension, preserves the exact response entity through the existing opaque upload boundary, and exposes fixed failures without logging URL query values or bodies. These controls narrow this explicit ingestion SSRF boundary; they do not establish safety for arbitrary network access.

Complete normalized Docling Markdown is split losslessly and deterministically, preferring Markdown boundaries with a UTF-8 ceiling of 1,800 bytes per fragment. This is deliberately below deployed `embeddinggemma`'s 2,048-token context; the 32 KiB Store item limit remains an independent absolute bound. Character offsets and fragment order reconstruct the exact normalized output. Preserved source bytes are read-only throughout OCR. Public canonical identity is stable from the downloaded source-byte digest, and `public-https`/`public-pdf` approval is accepted only with the server-only `owner-public-url-route` origin and approved local reference.

Librarian public/private/network ingestion and Coder artifact ingestion remain pending. Candidate-validation code and isolated policy tests do not constitute a trusted specialist production caller. No specialist currently supplies a genuine server handoff; those paths remain fail-closed/unreachable even though manual owner public ingestion is complete. Specialists neither communicate directly nor receive persistence credentials.

### 10. Keep session-document references in authoritative thread state

Each LangGraph thread may retain an ordered set of at most 100 unique stable document IDs in its checkpointed execution state. The authoritative thread ID comes from the authenticated current thread/run, never a browser- or model-selected alternate scope. Reopening that thread restores the set; another thread has its own set and may reference any of the same canonical document IDs. A link is only the thread/session identity plus document ID: it contains no document text, fragment text, tags, title, provenance, or other copied corpus metadata. Session links are thread-scoped execution references, not cross-session memory, not a second corpus, and not a second document copy.

Manual add and remove mutate only this bounded current-thread set after server authorization and exact canonical-document validation. Removing a link leaves the canonical document and every other thread's link unchanged. Session Documents resolves linked IDs against the current canonical metadata/lifecycle state by stable exact Store keys, so unavailable records fail closed and tag changes appear consistently in every session without rewriting links.

### 11. Use deterministic server operations over one canonical Store corpus

Jasper tools and manual Installation Library reads both execute server-side over the Agent Server-injected `BaseStore` through `StoreCapabilities`, but use deliberately different transports. Jasper receives bounded model-facing graph tools through `Runtime.store`. The browser calls authenticated custom Phase 5 FastAPI routes; those routes verify auth-first `Request.user` and use the documented custom-route `langgraph.config.get_store()` injection added in Agent Server v0.7.22. The browser supplies a bounded operation envelope, never a Store namespace, tenant, trust domain, owner, credential-derived scope, or Phase 5 persistence handle.

The manual read route supports exact canonical resolution, allowlisted canonical metadata filtering, and bounded semantic fragment search. Separate deterministic owner-ingestion routes accept only the sidecar's opaque file reference plus matching filename/title/tags, or a bounded public HTTPS URL/title/tags; neither has a model-visible tool form or exposes a scope or identity selector. Semantic mode delegates ranking to `BaseStore.asearch`, preserves native order/scores while deduplicating by canonical document, verifies active lifecycle, and returns canonical metadata only. Search is limited to 20 documents and queries to 4 KiB before Store access. Direct Phase 5 Store get/search/put/delete/list-namespaces remains denied; existing owner-prefixed legacy Store behavior is preserved.

Search requests do not change thread links. If Jasper actually uses a returned excerpt as evidence, the successful exact fragment-use tool records that stable document ID in authoritative current-thread state; merely appearing in search results does not link it. Linking never injects a full document into model context. The only in-scope frontend additions remain **Installation Library** and **Session Documents**. They use the existing TanStack Query provider around authenticated custom-route calls and current-thread SDK run mutations; the browser is a cache/projection, never an authority or shadow corpus. Cache partitioning uses a stable non-secret auth discriminator, not a raw credential.

## Risks / Trade-offs

- Namespace mistakes could disclose content; derive all scope server-side and test each namespace dimension.
- BaseStore has no compare-and-swap or multi-key transaction. Phase 5 must not claim conflicting-write safety and must not add a custom locking or transaction layer.
- Local semantic ranking depends on Ollama and `embeddinggemma`; keep that provider inside the approved local trust boundary, preserve native scores/order, sanitize failures, and retain hard candidate/response bounds. Memory lexical matching remains truthfully labeled.
- Deletion timing can regress; test immediate exclusion, both sides of the exact seven-day boundary, restore ownership, and permanent purge.
- Documents can contain prompt injection; treat text as data and keep policy outside retrieval content.
- Documentation writes are not multi-key transactions. Validate before mutation, sanitize failures, and do not claim transactional rollback or all-or-nothing backend behavior.
- Thread-link and corpus operations are separate persistence surfaces without a cross-surface transaction. Add a link before claiming Jasper used a document, fail safely if persistence fails, and do not claim atomic checkpoint/Store behavior.
- Client caches can become stale; TanStack Query is a projection only, and every search and mutation must be reauthorized against server-owned corpus and thread state.

## Migration Plan

1. Inventory deployed Store behavior, identity/configuration, persistence boundaries, and lexical support.
2. Implement fail-closed authentication, capability authorization, and namespace boundaries over the injected Store.
3. Prove browser and agent identities receive no database credential or direct internal-table operation.
4. Add lifecycle, audit, ingestion, isolation, race, bounds, injection, credential-leak, canonical-corpus/tag, thread-link, shared-retrieval-contract, exact-key, excerpt-context, TanStack-view, and deployed authorization tests.
5. Enable only after focused acceptance testing and human release approval. Preserve the database, named volume, and sessions. The running deployment contains no Phase 5 code or data, including no canonical Phase 5 document-link data, so this simplification requires no Phase 5 data migration and performs no database ownership migration.
